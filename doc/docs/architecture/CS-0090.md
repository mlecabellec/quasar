# Constraint 0090

## Title
Formal C++ Commenting, Doxygen & Traceability Standards

## Description

This constraint applies to all C++ header (`.h`, `.hpp`) and source (`.c`, `.cpp`) files within the Quasar project (excluding `cmake-projects/third-party` and `ext-projects`). It consolidates and formalizes the commenting obligations introduced in [CS-0010.44](CS-0010.md), [CS-0010.45](CS-0010.md), [CS-0020.61](CS-0020.md), [CS-0020.77](CS-0020.md), and [CS-0030.1 - CS-0030.2](CS-0030.md), aligning Quasar with Doxygen 1.9.8+ and safety-critical formal documentation standards (MISRA C++:2023, DO-178C, ECSS-E-ST-40C, JSF AV C++, and Design by Contract).

Regarding this constraint, the following rules apply:

### 1. Structural Coverage & Doxygen Compatibility
- **[CS-0090.1] Universal Entity Doxygen Coverage (`@brief` and `@details`)**: Every C++ declaration and definition — including **namespaces, classes, structs, scoped/unscoped enums, enumerators, type aliases, fields, static/instance members, constants (`constexpr`/`const`), constructors, destructors, methods, operators, and free/namespace functions** — MUST be preceded (or inline-annotated with `///<`) by a valid Doxygen comment block (`/** ... */` or `/// ...`).
  - **Paired `@brief` + `@details` Structure**: Every Doxygen block MUST include a concise, single-sentence `@brief` summary suitable for Doxygen summary tables and collaboration graphs. Usage of `@details` alongside `@brief` is strongly encouraged for all APIs and **mandatory** for non-trivial classes, state machines, fields, and methods in order to separate high-level intent (`@brief`) from operational mechanics, concurrency guarantees, ownership, and edge-case semantics (`@details`).
  - All custom traceability and structural tags (`@task`, `@requirement`, `@constraint`, `@rule`, `@feature`, `@exposed`, `@compliance`, `@rationale`, `@consumed`, `@error`, `@containment`) MUST match the `ALIASES` registered in `Doxyfile-html` and `Doxyfile-pdf1` so `doxygen` parses all sources with **zero unknown-command or undocumented-entity warnings**.

### 2. Traceability & Compliance Justification
- **[CS-0090.2] Mandatory Reference Citation & Compliance Proof**: Every documented **method, function, field, member, structure (`class`/`struct`/`enum`), and constant** MUST explicitly cite:
  1. **Originating Reference (`@task`, `@requirement`, `@constraint`, `@rule`, `@feature`)**: The exact identifier(s) (e.g., `TSK-YYYYMMDD-NNN`, `REQ-NNNNN`, `CS-NNNN.X`, `FE-NNNN`, `UC-NNNN`) that justified introducing or modifying the item. Vague prose without item IDs is forbidden.
  2. **Exposed Boundary Tag (`@exposed`)**: Required whenever the entity forms part of an external/module/script/network boundary ([CS-0030.2]).
  3. **Compliance Mechanism (`@compliance`)**: A concrete explanation of *how* the item satisfies the cited constraints and requirements (e.g., thread safety via `std::timed_mutex`, bounded iteration via `MAX_*`, RAII ownership, `noexcept` guarantee, or explicit width typing).

### 3. Complete Parameter, Return Value & Error Contracts
- **[CS-0090.3] Formal Parameter Contract (`@param[in|out|in,out]`)**: Every parameter of every method, constructor, function, and documented template MUST use Doxygen directional syntax (`@param[in]`, `@param[out]`, or `@param[in,out]`) and MUST explicitly document all four required properties:
  1. **`Justification:`** Why the parameter is required by the signature and what architectural role it fulfills.
  2. **`Usage:`** How the implementation reads, inspects, forwards, transforms, or writes the parameter.
  3. **`Consumed:`** Explicit statement of whether the parameter is consumed or has its observable properties altered during execution (`No (read-only const ref)`, `Yes (moved-from via std::move; caller retains empty state)`, or `Mutated in-place (advances cursor and populates buffer)`). Transfer-of-ownership parameters SHOULD also cross-reference `@consumed` when clarifying move semantics ([CS-0010.2]).
  4. **`Prerequisites:`** Concrete preconditions (`@pre` / `Prerequisites:`) covering nullability (`!= nullptr`), mandatory populated fields, valid numeric ranges, units, alignment, container cardinality (e.g., `!empty()`, `size() >= HEADER_BYTES`), and required caller/object state invariants.
- **[CS-0090.7] Formal Return Value Contract (`@return` & `@retval`)**: All commenting requirements applicable to parameters ([CS-0090.3]) apply symmetrically to every non-`void` return value documented under `@return` (complemented by `@retval` for discrete sentinel, boolean, or error-code outcomes). Every `@return` specification MUST define:
  1. **`Justification:`** Why this value/wrapper is returned and what caller decision or data flow it enables.
  2. **`Usage:`** How callers are expected to inspect, unwrap, move, or propagate the returned value.
  3. **`Consumed:` / `Ownership:`** Whether ownership is transferred (move-returned value / `std::unique_ptr`), shared (`std::shared_ptr`), or borrowed (`const T&`, `std::span`), and whether extracting the payload consumes internal staging state.
  4. **`Prerequisites:` / Postconditions:** Conditions guaranteed upon return (`@post`) and prerequisites required before dereferencing or consuming the result.
  5. **`Limitations:`** Operational boundaries on the returned object (thread-affinity, single-consumer restriction, valid call sequence, or view invalidation triggers).
  6. **`Lifecycle:`** Exact validity window (e.g., independent caller-owned value vs reference/view valid only until next mutating method call or enclosing object destruction).
  7. **`Modification / Deletion:`** Explicit statement of whether callers are permitted or forbidden to mutate, move-from, reset, or explicitly destroy/release the returned object or resource handle.
  8. **`Specific Values:`** Meaning of all sentinel, boolean, boundary, or discriminated outcomes (e.g., `true`, `false`, `nullptr`, `0`, `-1`, `std::nullopt`, or `std::expected` value vs error payload, documented with `@retval` where discrete).
  9. **`Error Behavior:`** Exact returned state, sentinel, or fallback value produced when any failure occurs (or confirmation that stack unwinding prevents a return object from being materialized).
- **[CS-0090.8] Error Categories, Failure Behavior & Containment Documentation**: Every function or component boundary capable of failing (via exceptions, `std::expected`/`Result<T>`, sentinel codes, fault counters, or timed waits) MUST define behavior by explicit error category and document error containment ([CS-0020.61], [CS-0020.77]):
  1. **Error Categorization & Behavior (`@error`, `@throws`, `@retval`)**: Classify potential failures into clear categories — such as **Validation / Contract**, **Transient / Timeout**, **Resource / Allocation**, **Hardware / Bus / I/O**, and **Fatal / Invariant Breach** — and specify for *each category*: the observable return/exception outcome, exception-safety level (no-throw, strong rollback, or basic), post-failure state of `this` and `[out]`/`[in,out]` arguments, diagnostic side effects, and recommended caller recovery (retry, reset, degrade, or abort).
  2. **Error Containment & Limitations (`@containment`)**: Document the active **containment approach** implemented at that boundary (e.g., RAII transaction rollback guards, copy-and-swap / staged commit before state mutation, `std::expected` error isolation preventing cross-thread exception termination, timed mutexes bounding deadlock propagation, bounded retry budgets, isolated per-slave/per-channel fault domains, or EtherCAT `SAFEOP` watchdog transitions) together with its explicit **limitations** (e.g., irreversible physical wire frames already transmitted, OS scheduler jitter exceeding timed-wait budget, basic guarantee clearing temporary scratch buffers, hardware power loss requiring physical re-init, or fatal invariant violations terminating execution).

- **[CS-0090.9] Formalization of Pre-Conditions, Post-Conditions & Invariants**: Developers are strongly encouraged to formalize interface contracts explicitly using Doxygen Design-by-Contract tags (`@pre`, `@post`, `@invariant`) expressed as verifiable logical predicates rather than vague prose, aligned with C++26 Contracts ([CS-0050.1]):
  - **Pre-Conditions (`@pre`)**: State the exact boolean/relational condition each caller MUST establish prior to invocation (e.g., `@pre frame_bytes.size() <= MAX_FRAME_BYTES`, `@pre slave_idx < MAX_SLAVES`).
  - **Post-Conditions (`@post`)**: State observable guarantees established on both normal and faulted return paths (e.g., `@post (result == true) ==> (out_record.valid == true)`, `@post (result == false) ==> unchanged(*this)`).
  - **Invariants (`@invariant`)**: State class, state-machine, or loop invariants preserved across public operations and lock acquisitions (e.g., `@invariant mutex_ serializes access to staging_`).
  - Wherever compiler and language standard permit, mirror Doxygen `@pre`/`@post` predicates directly in executable C++26 contract annotations (`[[expects: ...]]`, `[[ensures: ...]]`) or explicit runtime guards.

### 4. Formal Safety-Critical Comment Hygiene (State of the Art)
- **[CS-0090.4] Formal Precision & Safety Hygiene**: Inspired by MISRA C:2023 Directive 4.4, JSF AV C++ Rule 9, DO-178C traceability mandates, and Design by Contract:
  - **No Commented-Out Code**: Inactive or obsolete source code MUST NOT remain commented out in headers or `.cpp` files; rely exclusively on Git history.
  - **Strict Basic ASCII Source Character Set**: Comments MUST contain strictly 7-bit printable ASCII characters (`0x20`–`0x7E`, tab/newline) to avoid toolchain encoding faults across compilers, Doxygen PDF generators, and static analyzers.
  - **No Nested Block Comments**: Reserve `/** ... */` for entity header blocks and `//` for inline/body comments. Never place `/*` inside another block comment.
  - **Design by Contract & Thread-Safety**: Document pre-conditions (`@pre`), post-conditions (`@post`), class/loop invariants (`@invariant`), side effects (`@par Side Effects:`), re-entrancy, and locking order (`@note`).
  - **Rationale Over Noise & UB Justification**: Inline comments MUST explain *why* (intent, invariant, hardware timing, ABI layout, or why an explicit cast / implementation-defined conversion is safe per [CS-0020.59]), never restate trivial C++ syntax.

### 5. In-Body Method Comments & Control Structure Documentation
- **[CS-0090.5] Mandatory In-Body Method Justifications**: Every method, constructor, or function body longer than 5 lines MUST contain inline `//` comments explaining algorithmic phases, synchronization/locking strategy, resource ownership decisions, error-handling paths, and compliance mechanics (reinforcing [CS-0010.44]: no uncommented block longer than 5 lines).
- **[CS-0090.6] Comprehensive Control Structure Documentation**: Every control structure — **`if`**, **`else if`**, **`else`**, **`switch`**, **`case`**, **`default`**, **`for`**, **range-`for`**, **`while`**, **`do-while`**, **`try`**, and **`catch`** — MUST be accompanied by an explanatory `//` comment immediately preceding (or inside the opening header/branch of) the control construct detailing how it operates:
  - **Condition / Branch Rationale (`if` / `else if` / `else` / `switch`)**: Explain the predicate semantics, state discriminator, and why an empty `else` or `default` branch is safe ([CS-0060.3]).
  - **Iteration Mechanism & Hard Bound (`for` / `while` / `do-while`)**: Explain loop progress, termination condition, invariant preserved on each step, and cite the hard limit constant (`MAX_*`) enforcing [CS-0010.37].
  - **Exception / Fault Handling (`try` / `catch`)**: Explain what failure sources may throw and how state/resources remain consistent during catch recovery ([CS-0010.20]).

## Standard Compliant Example

```cpp
/**
 * @brief Decode wire bytes into a validated telemetry record.
 *
 * @details Validates frame bounds under timed-mutex exclusion and transfers
 * caller staging storage via move semantics.
 *
 * @task TSK-20261113-003
 * @requirement REQ-00010
 * @constraint CS-0010.2, CS-0010.37, CS-0010.46, CS-0090.1, CS-0090.3, CS-0090.7, CS-0090.8, CS-0090.9
 * @feature FE-0010
 * @compliance Enforces bounded iteration via MAX_ITEMS, explicit types (no auto),
 * timed locking, checked std::span access, full return contract, and error containment.
 *
 * @param[in] frame_bytes
 *   Justification: Supplies incoming raw wire bytes to decode.
 *   Usage: Read sequentially without modifying caller memory.
 *   Consumed: No (read-only std::span view).
 *   Prerequisites: Non-empty when payload expected; size() <= MAX_FRAME_BYTES.
 * @param[in,out] scratch_buf
 *   Justification: Reuses pre-allocated temporary buffer across decode cycles.
 *   Usage: Moved into internal staging storage on lock acquisition.
 *   Consumed: Yes (moved-from via std::move; caller retains valid empty vector).
 *   Prerequisites: Valid initialized std::vector instance (may be empty).
 * @param[out] out_record
 *   Justification: Delivers decoded telemetry fields without extra allocation.
 *   Usage: Fields overwritten deterministically upon successful decode.
 *   Consumed: No (output target; prior caller values are replaced).
 *   Prerequisites: Mutable caller-owned TelemetryRecord reference.
 *
 * @pre frame_bytes.size() <= MAX_FRAME_BYTES
 * @post out_record.valid == true on true return
 * @invariant Internal mutex_ serializes staging_ access across threads.
 * @return bool
 *   Justification: Reports deterministic commit vs timed-lock backpressure status.
 *   Usage: Caller branches directly on returned boolean before reading out_record.
 *   Consumed: Value returned by copy; caller obtains independent scalar status.
 *   Prerequisites: Out parameter out_record bound prior to call; discard forbidden ([[nodiscard]]).
 *   Limitations: Boolean does not encode frame byte length; inspect out_record.byte_count on true.
 *   Lifecycle: Standalone temporary prvalue valid in caller expression scope.
 *   Modification / Deletion: Immutable rvalue; mutable binding by caller permitted; no delete needed.
 *   Specific Values: true (decoded & committed); false (timed lock acquisition expired).
 *   Error Behavior: Returns false cleanly on lock timeout; throws before return on validation/alloc failure.
 * @retval true Decode succeeded and out_record populated atomically under mutex_.
 * @retval false Timed lock LOCK_TIMEOUT expired; internal state unchanged and out_record.valid = false.
 * @throws std::length_error [Validation / Contract] Thrown before state mutation if frame_bytes.size() > MAX_FRAME_BYTES.
 * @error
 *   - Validation / Contract (frame_bytes.size() > MAX_FRAME_BYTES): Throws std::length_error; strong guarantee (this and scratch_buf untouched).
 *   - Transient / Timeout (mutex_ lock contention > LOCK_TIMEOUT): Sets out_record.valid = false and returns false; no-throw.
 *   - Resource / Fatal (allocator failure if vector grows later): Stack unwinds cleanly via RAII lock release.
 * @containment
 *   Approach: Bounds check precedes timed_mutex lock (strong guarantee on validation); std::unique_lock
 *   enforces RAII unlock and deterministic timeout boundary preventing deadlock cascades.
 *   Limitations: Under severe RT scheduling jitter, timed wait may return false early requiring caller retry;
 *   cannot recover if caller supplies corrupted wire bytes fitting within MAX_FRAME_BYTES.
 */
[[nodiscard]] bool decode_frame(std::span<const std::byte> frame_bytes,
                                std::vector<std::byte> &&scratch_buf,
                                TelemetryRecord &out_record) {
  // Guard against oversized payloads prior to locking to keep critical section deterministic [CS-0010.37].
  if (frame_bytes.size() > MAX_FRAME_BYTES) {
    throw std::length_error{"Frame exceeds MAX_FRAME_BYTES"};
  } else {
    // Size is within upper bound; proceed to timed lock acquisition [CS-0060.3].
  }

  // Acquire timed mutex to prevent unbounded thread stalls under contention [CS-0010.26, CS-0010.46].
  std::unique_lock<std::timed_mutex> lock{mutex_, LOCK_TIMEOUT};
  // Abort cleanly if lock timed out so real-time caller can recover deterministically.
  if (lock.owns_lock() == false) {
    out_record.valid = false;
    return false;
  } else {
    // Mutex held; safe to move caller staging buffer into member state.
  }

  // Consume caller scratch storage via move semantics to avoid heap reallocation [CS-0010.2].
  staging_ = std::move(scratch_buf);
  out_record.byte_count = frame_bytes.size();
  out_record.valid = true;
  return true;
}
```

## Rationale

High-integrity industrial automation software requires every abstraction, parameter contract, invariant, and branch decision to be auditable without guessing author intent. Integrating formal Design by Contract (`@pre`, `@post`, `@invariant`), mandatory parameter semantics (`Justification`, `Usage`, `Consumed`, `Prerequisites`), bidirectional requirement/task traceability, and mandatory control-flow/in-body explanations guarantees both human auditability and strict automated verification.

## Verification

*Note: These methods are not exhaustive. The developer (human or agent) SHALL ensure that applied verification is effective to ensure compliance and SHALL add verifications if required on a case-by-case basis.*

Each rule must be covered by at least two scriptable verification methods:

- **Method 1: Doxygen Documentation Engine (`doxygen`)**
  - Execute `doxygen Doxyfile-html` with `EXTRACT_ALL = NO`, `WARN_IF_UNDOCUMENTED = YES`, `WARN_NO_PARAMDOC = YES`, `WARN_IF_DOC_ERROR = YES`, `WARN_IF_UNDOC_ENUM_VAL = YES`, and Quasar `ALIASES` active. Verifies `[CS-0090.1, CS-0090.2, CS-0090.3]`.
  - Run CI checks with `WARN_AS_ERROR = FAIL_ON_WARNINGS` on compliant modules.
- **Method 2: AST & Annotation Auditor (`helpers/check_annotations.py`)**
  - Uses `libclang` AST traversal (`clang.cindex`, `-std=c++23`) paired with structural comment inspection to verify:
    - `@brief` (and `@details` on non-trivial APIs) across classes, structs, enums, fields, members, constants, and methods `[CS-0090.1]`.
    - Traceability tags (`@task`/`@requirement`/`@constraint`/`@rule`/`@feature`/`@exposed`) and `@compliance` `[CS-0090.2]`.
    - Directional `@param[in|out|in,out]` plus `Justification`, `Usage`, `Consumed`, and `Prerequisites` `[CS-0090.3]`.
    - Full `@return` contract (`Justification`, `Usage`, `Consumed`, `Prerequisites`, `Limitations`, `Lifecycle`, `Modification`/`Deletion`, `Specific Values`, `Error Behavior`) on non-`void` methods `[CS-0090.7]`.
    - Error-category behavior (`@throws`/`@error`/`@retval`) and containment/limitation documentation (`@containment`) `[CS-0090.8]`.
    - Advisories encouraging formal predicate `@pre`/`@post`/`@invariant` contracts `[CS-0090.9]`.
    - In-body justification comments `[CS-0090.5]` and control structure comments `[CS-0090.6]`.
- **Method 3: Compliance Suite & Static Hygiene (`helpers/compliance_suite.py` & `helpers/check_metrics.py`)**
  - Scans source files for commented-out code heuristics, non-ASCII characters in comments `[CS-0090.4]`, uncommented blocks > 5 lines `[CS-0010.44, CS-0090.5]`, missing `else` branches `[CS-0060.3]`, and function/class size metrics `[CS-0010.35, CS-0010.36]`.
- **Method 4: Compiler & Static Analyzer Checks (`clang++ -Wdocumentation` & `clang-tidy`)**
  - Compile headers/sources with `-Wdocumentation` to cross-verify Doxygen parameter names and command correctness `[CS-0090.1, CS-0090.3]`.
