# Goal

Implement advanced EtherCAT network engineering capabilities, including an ENI (EtherCAT Network Information) skeleton generator, Hot Connect support, and an ESI (EtherCAT Slave Information) management system for `resoem`.

# Details

## Context
Standard EtherCAT deployment often suffers from "position-dependency," where removing a single slave or changing the order breaks the system. This task introduces professional-grade configuration tooling and dynamic topology management to make Quasar-based EtherCAT systems modular and resilient to hardware failures.

## Requirements

### 1. ENI Skeleton Generation Tool (`ecat-eni-gen`)
- [ ] [TSK-20260410-002.1] **Live Topology Extraction**: Scan the physical bus and extract identity (Vendor, Product, Revision) and current CoE PDO mappings for all slaves.
- [ ] [TSK-20260410-002.2] **ETG.2100 XML Generation**: Implement a generator that produces a strictly compliant (or "good enough" for industrial masters) ETG.2100 ENI file.
- [ ] [TSK-20260410-002.3] **Initialization Command Scaffolding**: Generate empty `<InitCmd>` blocks for each transition (I->S, S->O) to be manually filled.

### 2. Validation & Loopback Testing
- [ ] [TSK-20260410-002.4] **ENI Bootstrapping Test**: Implement an optional test (disabled by default) that:
    1. Generates an ENI file from a live bus.
    2. Restarts the master using the generated ENI file as its primary configuration source.
    3. Verifies that all slaves reach the **OP** state and process data matches the previous run.

### 3. ESI Management & E²PROM Tools
- [ ] [TSK-20260410-002.5] **Station Alias Manager**: A tool (`ecat-alias`) to read/write the Station Alias in the slave's E²PROM to support Hot Connect identification.
- [ ] [TSK-20260410-002.6] **Binary E²PROM Access**: Implement raw read/write methods for slave E²PROM (needed for recovery).

### 4. Hot Connect & Topology Resilience
- [ ] [TSK-20260410-002.7] **Alias-Based Discovery**: Enhance `resoem` to identify slaves by their **Station Alias** rather than their physical bus position.
- [ ] [TSK-20260410-002.8] **Optional Slave Support**: Allow `EthercatMasterService` to define "Expected" vs. "Present" slaves. The system must remain operational if an "Optional" slave is missing.
- [ ] [TSK-20260410-002.9] **Dynamic Topology Reconstruction**: Implement a background routine that can re-initialize a newly connected slave (Hot Connect) without affecting the process data of existing slaves.

### 5. Deferred Features (Low Priority)
- [ ] [TSK-20260410-002.10] **FoE (File over EtherCAT)**: Support firmware transfer to slaves.
- [ ] [TSK-20260410-002.11] **EoE (Ethernet over EtherCAT)**: Provide a virtual network interface to allow standard TCP/IP communication.

# Implementation Plan

1. **Tooling Base**: Develop the `ecat-alias` tool to enable slave identification via E²PROM.
2. **XML Engine**: Integrate a lightweight XML generator (like `tinyxml2`) to handle the ENI output.
3. **Resoem Core Update**: Refactor the slave discovery logic to use a "Binding Map" (Alias -> NamedObject) instead of a simple index.
4. **Resilience Layer**: Implement the "Masking" logic in the Process Data loop to handle missing slaves.
5. **FoE/EoE Integration**: Utilize the underlying SOEM mailbox handlers to expose file and network bridges.

# Test and validation

- **ENI Interoperability**: Verify that the generated skeleton can be parsed by the Quasar configuration loader.
- **Hot Connect Stress**: Repeatedly plug/unplug a slave while a second slave is moving a motor; verify zero jitter or interruptions on the active slave.
- **Alias Conflict**: Verify that the master correctly handles two slaves with the same alias by throwing a descriptive configuration error.
