# Goal

Implement comprehensive CAN (Controller Area Network) bus support within the Quasar framework, including a hardware abstraction layer for SocketCAN, integration with the `datacodec` system for signal decoding, and a scripting plugin for Lua.

# Details

## Context

To enable Quasar's use in automotive, aerospace, and industrial automation contexts, it must provide high-performance, real-time access to CAN networks. This task focuses on bridging the low-level Linux SocketCAN API with Quasar's high-level `ActiveEntity` and `NamedObject` hierarchy, allowing scripts and C++ components to interact with CAN devices seamlessly.

## Requirements

- [ ] [TSK-20260311-006.1] **SocketCAN Driver**:
    - [ ] [TSK-20260311-006.1.1] Implement a C++ wrapper for the Linux SocketCAN kernel API.
    - [ ] [TSK-20260311-006.1.2] Support standard CAN 2.0B and CAN FD (Flexible Data-rate) frames.
    - [ ] [TSK-20260311-006.1.3] Support non-blocking I/O and asynchronous event notification (via `epoll` or `asio`).
- [ ] [TSK-20260311-006.2] **CAN ActiveEntity**:
    - [ ] [TSK-20260311-006.2.1] Create `CanDevice` inheriting from `ActiveEntity`.
    - [ ] [TSK-20260311-006.2.2] Implement lifecycle hooks: `initialize` (interface selection), `start` (open socket), `stop` (close socket).
    - [ ] [TSK-20260311-006.2.3] Expose interface statistics (RX/TX counts, errors) as reflexive fields.
- [ ] [TSK-20260311-006.3] **Signal Decoding (Datacodec Integration)**:
    - [ ] [TSK-20260311-006.3.1] Integrate with `FE-0090` (Datacodec) to allow mapping CAN frame payloads to `NamedObject` hierarchies.
    - [ ] [TSK-20260311-006.3.2] Support loading signal definitions from external configurations (e.g., JSON-based DBC equivalents).
- [ ] [TSK-20260311-006.4] **Lua CAN Plugin**:
    - [ ] [TSK-20260311-006.4.1] Implement `registerPluginComponents` for the CAN module.
    - [ ] [TSK-20260311-006.4.2] Provide Lua APIs for sending raw frames: `device:send(id, data, flags)`.
    - [ ] [TSK-20260311-006.4.3] Provide Lua APIs for receiving frames via callbacks: `device:onReceive(callback)`.
- [ ] [TSK-20260311-006.5] **Filtering & Bus Management**:
    - [ ] [TSK-20260311-006.5.1] Implement hardware-level ID filtering (using `CAN_RAW_FILTER`).

## Implementation Plan

1. **Hardware Layer**: Develop `SocketCanSocket` class in a new `cmake-projects/can` module.
2. **Entity Integration**: Implement `CanDevice` wrapping the socket and exposing it to the Quasar service registry.
3. **Codec Bridge**: Create a `CanFrameMapper` that uses `ContainerDef` to pack/unpack bit-level signals.
4. **Scripting Bindings**: Map `CanDevice` and `CanFrame` to Lua using `sol2`.
5. **Testing Infrastructure**: Set up integration tests using `vcan0` on Linux.

# Test and validation

- **Loopback Validation**: Verify that frames sent on `vcan0` are correctly received and parsed by a second `CanDevice` instance.
- **FD Support**: Verify that frames with up to 64 bytes of payload are correctly handled when CAN FD is enabled.
- **Performance**: Benchmark the decoding rate; ensure it can handle a fully loaded 1Mbps bus (approx. 8000 frames/sec) with minimal CPU overhead.
- **Error Handling**: Validate system behavior during bus-off conditions or when malformed frames are received.
- **ASan/TSan**: Run tests under sanitizers to ensure thread-safety of the asynchronous reception loop.

## Expected result

A high-performance CAN bus integration module allowing Quasar to interact with physical and virtual CAN networks with signal-level transparency.
