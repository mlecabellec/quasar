# Goal

Expose quasar classes to python.

# Details

## Context

Exposing classes to Python natively enables high-performance analytical tools to interface directly with active system data, fulfilling critical project data engineering requirements.

## Requirements

- [TSK-20260303-004.1] Expose quasar classes to python.
- [TSK-20260303-004.2] Select and integrate a C++/Python binding framework (e.g., pybind11 or nanobind).
- [TSK-20260303-004.3] Define mapping for fundamental types and containers from `coretypes`.
- [TSK-20260303-004.4] Map class hierarchies and interfaces from `named` to Python classes.
- [TSK-20260303-004.5] Configure CMake build system to generate Python extension modules (.so/.pyd).
- [TSK-20260303-004.6] Implement memory management strategies for shared ownership between C++ and Python.
- [TSK-20260303-004.7] Generate Python type stubs (.pyi) for static analysis and IDE autocompletion.
- [TSK-20260303-004.8] Establish a pytest-based validation suite for the exposed API.





## Implementation Plan

### Phase 1: Infrastructure & Framework Setup
1. **Framework Integration**: Evaluate and integrate `nanobind` (preferred over `pybind11` for modern C++ and performance) using CMake `FetchContent` to ensure seamless native build processes without external dependency burdens.
2. **CMake Build Configuration**: 
   - Configure CMake to locate standard Python environments (Python 3.11 for Debian 12, Python 3.12 for Debian 13).
   - Define a new target, `quasar_py`, as a Python extension module.
   - Configure compiler flags for optimal performance and cross-platform generation (`.so` for Linux).

### Phase 2: Core Types & Ownership Strategy
3. **Core Types Bridge (`coretypes`)**: Implement type casters and bindings for Quasar's fundamental classes, enumerations, and STL containers used across the codebase.
4. **Memory Management Architecture**: 
   - Define specific ownership semantics using C++ smart pointers (`std::shared_ptr`, `std::unique_ptr`).
   - Determine and implement explicit return value policies (`return_value_policy::reference`, `take_ownership`, etc.) to safely manage lifetimes spanning the Python and C++ boundary boundary without leaks.

### Phase 3: Advanced Module Bindings & Polymorphism
5. **Class Hierarchy Mapping (`named` module)**: 
   - Bind the generic interfaces and base hierarchy components of the `named` module.
   - Implement C++ trampoline classes designed to enable robust virtual method overriding from Python, thereby permitting dynamic polymorphism across language borders.
6. **Concurrency & Thread Safety**: 
   - Implement explicit Global Interpreter Lock (GIL) acquisition and release scopes (`gil_scoped_release` / `gil_scoped_acquire`) around blocking or long-running C++ routines.

### Phase 4: Validation, Stubs & Tooling
7. **Type Stubs Generation**: Automate the generation of comprehensive Python type stubs (`.pyi`) using `nanobind-stubgen` integrating them into the build process to guarantee static type checking and IDE autocompletion.
8. **Automated Testing Suite**: 
   - Develop comprehensive unit tests using `pytest` to validate the exposed C++ API directly from Python.
   - Implement specific stress tests covering edge-cases involving cyclic object graph ownership, structured C++ exception propagation into Python, and multithreading behavior.


# Test and validation

- Build and run the `nanobind` extensions against the system-default Python versions: Python 3.11 (**Debian 12**) and Python 3.12 (**Debian 13**).
- Verify totally stable cross-boundary memory sharing without faults.
- Implement extensive `pytest` suites covering edge cases of C++/Python object graph ownership and structured exception propagation.
- Validate multithreaded access functionality by verifying proper acquisition and release of the Python Global Interpreter Lock (GIL).

## Expected result

High-performance Python extension modules (.so/.pyd) that expose quasar's core interfaces to external Python environments securely and idiomatically.
