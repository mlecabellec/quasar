# Goal

The goal of this task is to enhance the scripting environement by:
    - completing the execution environement with pluggable and extendable components.
    - adding an executable target for the scripting environement.
      - The executable target should be able to load and execute scripts.
      - The executable target should be able to load and execute scripts from the command line.
      - The executable target should be able to load and execute scripts from stdin
      - The executable target should be able to load shared library exposing pluggable components.
        - The shared library should be able to register components to the execution environement.
        - The shared library should expose entry points allowing the execution environement to list, instantiate and call the components.
        
      
    

# Details

## Context

The current scripting environment within Quasar lacks a standalone runner, limiting its use to embedded contexts. Furthermore, extending the base environment currently requires recompilation of the core engine. To improve modularity and enable rapid development of new script-accessible features, a standalone executable target and a dynamic plugin system (via shared libraries) are needed. This allows extending the core scripting capabilities dynamically at runtime without altering the primary binaries.

## Requirements

- [ ] [TSK-20260310-001.1] **Standalone Executable**: Create a new executable target (e.g., `quasar-script-runner` or 'sre' for short) that initializes the scripting environment.
- [ ] [TSK-20260310-001.2] **File and Stdin Execution**: Implement support in the executable to read and execute scripts from a file path provided via the command line, and from standard input (`stdin`) if no file is provided.
- [ ] [TSK-20260310-001.3] **Dynamic Library Loading**: Implement a plugin loader to dynamically load shared libraries at runtime.
- [ ] [TSK-20260310-001.4] **Component Registration API**: Define a standard ABI entry point that shared libraries must implement to register their pluggable components with the execution environment.
  - [ ] [TSK-20260310-001.4.1] Complete ScriptableNamedObject to support dynamic registration and allowing to use it as pluggable component.
- [ ] [TSK-20260310-001.5] **Component Instantiation**: The execution environment must be able to discover, list, instantiate, and invoke methods on the loaded components through the scripting interface.

## Implementation Plan

1. **Executable Setup**: Define the executable target in the build system and implement the `main` entry point.
2. **Input Handling**: Implement parameter parsing to handle both file inputs and reading from standard input.
3. **Plugin System**: Build the DLL/SO dynamic loader component (e.g., using `dlopen`/`dlsym`).
4. **API Contract**: Define the standard header/interface that shared libraries will use to expose their components to the execution environment.
5. **Integration**: Connect the loaded components to the scripting engine so that they are exposed and usable from within the scripts.

# Test and validation

- **File Execution Validation**: Invoke the executable passing a simple script via command line argument and verify successful execution and output.
- **Stdin Execution Validation**: Pipe a script into the executable via standard input and ensure it executes accurately.
- **Plugin Loading & Interoperability**: Create a mock shared library plugin, load it at runtime, and verify that its components can be listed, instantiated, and called within a test script without crashing or memory leaks.
- **Error Handling**: Verify system resilience against invalid file paths, syntax errors in standard input, and attempts to load malformed or incompatible shared libraries.

## Expected result

A functional standalone scripting executable capable of running scripts from various input sources and dynamically expanding its component registry via shared libraries at runtime.
