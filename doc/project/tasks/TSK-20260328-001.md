# Goal

Implement a reflexive execution and service orchestration layer within the `quasar::named` library. This involves creating `NamedMethod` for executable logic, `NamedLuaMethod` for scriptable behavior, and `NamedService` for autonomous, threaded operations that serve as frontends for various system functionalities.

# Details

## Context
While the current `NamedObject` hierarchy effectively represents system state, it lacks a native, uniform way to encapsulate *behavior*. This task introduces the "Method-as-Object" and "Service-as-Object" patterns. By representing logic as child nodes, we allow scripts and remote interfaces (like Web UI or OPC UA) to discover and trigger system actions dynamically. `NamedService` extends this by providing an autonomous execution context (a dedicated thread) that uses these methods as lifecycle hooks.

## Proposed Solutions for Parameters and Return Values
To maintain consistency with the hierarchical nature of Quasar, the following mechanisms are proposed for `NamedMethod`:

1.  **Contextual Parameter Tree**: Methods accept a `std::shared_ptr<NamedObject>` as an input argument. This object can be a `NamedMap` or a custom tree structure containing named parameters.
2.  **Synchronous Return Object**: Methods return a `std::shared_ptr<NamedObject>`. For simple values, a `NamedVariant` or `NamedInteger` is used; for complex results, a dedicated tree is returned.
3.  **Reflexive Signature**: `NamedMethod` can optionally contain a `Schema` child node (using `datacodec` definitions) that describes the expected parameter types and return structure for validation before execution.

# Implementation Plan

1.  **Core Methods**: Implement the `NamedMethod` base class and the `invoke()` interface in `cmake-projects/named`.
2.  **Lua Bridge**: Expand the scripting engine to handle the new method types, ensuring `sol2` can call C++ lambdas and vice-versa.
3.  **Service Backbone**: Implement the `NamedService` threading logic, utilizing `std::stop_token` (C++20) for clean service termination.
4.  **Reflexive Hooks**: Write the logic that scans for "configure", "run", etc., by name within the service's children.
5.  **Validation**: Create a mock service in Lua that performs a simple calculation in its "run" loop and exposes its results via a `NamedInteger` sibling.

# Test and validation

- **Method Dispatch**: Verify that a lambda-based `NamedMethod` correctly accesses its parent's data and returns a valid result tree.
- **Lua Interop**: Verify that a C++ service can execute a `NamedLuaMethod` hook without state corruption.
- **Thread Safety**: Stress-test starting and stopping 100 `NamedService` instances concurrently.
- **Frontend Exposure**: Verify that an external interface (e.g., a simulated OPC UA node) can "see" and "call" a `NamedMethod` attached to a service.

## Expected result

A versatile, reflexive framework where behavior is as discoverable and manageable as data, enabling complex service-oriented architectures within Quasar.
