# Goal

Perform intensive validation and enhancement of the Lua execution environment to ensure robust integration with Quasar's core systems (`NamedObject`, `ActiveEntity`) and dynamic plugin infrastructure.

# Details

## Context

The scripting environment is a central part of Quasar, allowing for dynamic behavior without recompilation. To guarantee industrial-grade reliability, the Lua bridge must be exhaustively tested across all interaction patterns: C++-to-Lua overrides, Lua-to-C++ method calls, event-driven notifications (Observer pattern), and runtime plugin extension. This task focuses on building a comprehensive "stress test" suite for the Lua engine and filling any identified gaps in the API bindings.

## Requirements

- [ ] [TSK-20260311-011.1] **Exhaustive Type & Hierarchy Validation**:
    - [ ] [TSK-20260311-011.1.1] Verify that all `NamedObject` variants (Integer, String, Buffer, etc.) can be instantiated, modified, and queried from Lua.
    - [ ] [TSK-20260311-011.1.2] Test complex tree manipulations from Lua (creating deep hierarchies, re-parenting, find-by-path).
- [ ] [TSK-20260311-011.2] **ActiveEntity Bridge Verification**:
    - [ ] [TSK-20260311-011.2.1] Ensure lifecycle methods (`initialize`, `start`, `stop`) can be invoked from Lua.
    - [ ] [TSK-20260311-011.2.2] Verify dynamic method execution (`ActiveEntity::execute`) with complex `NamedObject` arguments passed from Lua.
    - [ ] [TSK-20260311-011.2.3] Validate reflexive field access (get/set) for `ActiveEntity` instances.
- [ ] [TSK-20260311-011.3] **Lua Observer Implementation**:
    - [ ] [TSK-20260311-011.3.1] Implement a `LuaObserver` class that allows a Lua function to be registered as an `IObserver` for any `ActiveEntity`.
    - [ ] [TSK-20260311-011.3.2] Verify that Lua-based observers correctly receive and process event payloads asynchronously.
- [ ] [TSK-20260311-011.4] **Native Lua API & Library Support**:

    - [ ] [TSK-20260311-011.6.2] Use TSan to verify that concurrent access to the same Lua state (if permitted) or multiple Lua states does not cause race conditions.

## Implementation Plan

1. **Test Infrastructure**: Enhance the `scripting/test` module with a "Mock Plugin" and "Mock ActiveEntity" for varied testing scenarios.
2. **LuaObserver implementation**: Create the necessary C++ bridge to allow Lua functions to satisfy the `IObserver` interface.
3. **Automated Test Suite**: Develop a collection of Lua test scripts covering the requirements and execute them via `gtest` using the `LuaEngine`.
4. **API Gap Filling**: Based on test failures, implement any missing bindings in `TypeBindings.hpp` or `RegistryBindings.hpp`.
5. **Stability Benchmarking**: Implement a "Script Stress" test that runs high-frequency interactions between Lua and C++ for extended periods.

# Test and validation

- **API Coverage**: Ensure 100% of public `NamedObject` and `ActiveEntity` methods are accessible and functional from Lua.
- **Asynchronous Correctness**: Verify that `LuaObserver` callbacks are executed in the correct order and handle event data without corruption.
- **Sanitizer Cleanliness**: All intensive tests must pass under **ASan** (no leaks) and **TSan** (no races).
- **Performance Baseline**: Document the overhead of calling a C++ method from Lua vs. a native Lua call.

## Expected result

A fully verified, bulletproof Lua environment with exhaustive test coverage and zero identified gaps in core system interoperability.
