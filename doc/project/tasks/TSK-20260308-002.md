# Goal

Provide a generic interface and implementation for 
- objects with limited relexivity capabilities on
  - Fields that are derived from NamedObject
  - Methods that are consuming NamedObjects as parameter and returning NamedOjects as results.
- objects implementing observer and producer pattern.
- objects intended to be used as services.
- object usable as interface with protocols and abstraction from hardware devices.

# Details

## Context

The Quasar architecture needs a standardized way to represent operational entities—such as hardware device abstractions, protocol interfaces, and background services—within the `named` object hierarchy. These entities require a structured mechanism for exposing their state (via fields derived from `NamedObject`), their capabilities (via reflexive methods consuming/returning `NamedObject`s), and their dynamic behavior (via observer/producer patterns for event-driven architectures). By unifying these under a generic interface, the system can systematically discover, monitor, and interact with complex components at runtime.

## Requirements

- [TSK-20260308-002.1] **Generic Interface**: Define an abstract base class (e.g., `ADevice` or `AService`) inheriting from `NamedObject` to represent active components like services and hardware abstractions.
- [TSK-20260308-002.2] **Reflexivity for Fields**: Implement a mechanism to register and query member variables (fields) that are themselves `NamedObject` derivatives, allowing for programmatic introspection of the entity's state.
- [TSK-20260308-002.3] **Reflexivity for Methods**: Implement a dynamic method dispatch system allowing the entity to register executable commands/methods that take a `NamedObject` (or variant) as input and return a `NamedObject` as output.
- [TSK-20260308-002.4] **Observer/Producer Pattern**: Integrate a thread-safe event subscription model (Publisher/Subscriber) within the interface, allowing external observers to be notified of state changes, data production, or specific events.
- [TSK-20260308-002.5] **Hardware & Protocol Abstraction**: Ensure the interface provides sufficient virtual hooks (`start`, `stop`, `initialize`, `reset`) to wrap complex underlying protocols and physical hardware interactions.
- [TSK-20260308-002.6] **Service Locator Integration**: Provide integration allowing these reflexive objects to be deployed, discovered, and managed as system-wide services.

## Implementation Plan

### Phase 1: Core Interfaces & Lifecycle Management
1. **Define Abstract Base**: Create `IActiveEntity` (or similar interface) inheriting from `NamedObject`.
2. **Lifecycle Methods**: Declare pure virtual hooks `initialize()`, `start()`, `stop()`, and `reset()`.
3. **State Tracking**: Implement an atomic internal state machine (e.g., Uninitialized, Ready, Running, Error) accessible via `NamedObject` properties.

### Phase 2: Observer/Producer Pattern Integration
1. **Observer Interface**: Define an `IObserver` interface with a `notify(const NamedObject& eventData)` method.
2. **Subscription Engine**: Implement a thread-safe registry in the base class to manage a collection of weak pointers to subscribers.
3. **Dispatch Mechanism**: Create asynchronous and synchronous notification dispatch functions for the producer to broadcast state changes and data payloads.

### Phase 3: Reflexivity Engine - Fields
1. **Field Registry**: Implement an internal data structure (e.g., `std::unordered_map`) mapping string names to references of child `NamedObject` fields.
2. **Registration API**: Provide protected macros or template methods (e.g., `REGISTER_FIELD(name, variable)`) to bind class members to the reflexivity engine during construction.
3. **Query Interface**: Expose `getField(name)` and `listFields()` methods for runtime introspection.

### Phase 4: Reflexivity Engine - Methods
1. **Command Abstraction**: Define a generic `ICommand` callable interface taking `const NamedObject& in` and returning a `NamedObject`.
2. **Method Binding**: Utilize `std::function` and template metaprogramming to wrap native C++ member functions into the `ICommand` interface.
3. **Execution Dispatcher**: Expose `execute(const std::string& methodName, const NamedObject& args)` to dynamically route calls.

### Phase 5: Service Integration & Validation
1. **Service Locator Integration**: Enable these reflexive components to register with the main Quasar `ServiceManager`.
2. **Reference Implementations**: Develop a fully functional mock hardware driver (e.g., `MockTemperatureSensor`) utilizing all reflexivity and observer features.
3. **Unit Tests**: Write comprehensive test cases targeting dynamic invocation, memory leaks (ASan), and concurrency (TSan).

# Test and validation

- **Reflexivity Test**: Verify that calling a registered method via the dynamic interface correctly executes the underlying C++ method and properly handles parameter passing and dynamic return types.
- **Event Dispatch Test**: Subscribe multiple observers to a producer and verify that all observers receive broadcasted data promptly and without data corruption or deadlocks under concurrent load.
- **Lifecycle Management**: Validate that starting, stopping, and resetting the service/device properly triggers the corresponding implementation hooks and updates the internal state.
- **Memory Leak & Cycle Check**: Run tests via Valgrind/ASan to ensure that the observer subscriptions do not create strong reference cycles (enforcing weak pointers) and that all dynamic fields are cleanly destructed.

## Expected result

A versatile, reflexive C++ base framework that standardizes how high-level logical components, services, and hardware abstractions are structured, interacted with, and monitored within the Quasar ecosystem.
