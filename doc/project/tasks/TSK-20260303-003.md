# Goal

Add support for lua scripting.

# Details

## Context

Providing a lightweight, embedded Lua scripting mechanism allows managing dynamically loadable system behavior without requiring binary recompilation, significantly accelerating the iteration cycle.

## Requirements

- [TSK-20260303-003.1] Add support for Lua.
- [TSK-20260303-003.2] Integrate `sol2` as the primary C++ wrapper for Lua 5.4.
- [TSK-20260303-003.3] Initialize a new CMake project `cmake-projects/scripting` to host the Lua engine and bindings.
- [TSK-20260303-003.4] Expose `quasar::coretypes` (e.g., `Variant`, `Timestamp`, `Status`) to the Lua environment using `sol::state_view`.
- [TSK-20260303-003.5] Expose `quasar::named` entities to allow Lua scripts to resolve and manipulate objects by name.
- [TSK-20260303-003.6] Implement a modular binding architecture to allow other `cmake-projects` libraries to register their own Lua APIs.
- [TSK-20260303-003.7] Define a `ScriptComponent` interface within the component system to allow Lua scripts to hook into lifecycle events (init, update, shutdown).
- [TSK-20260303-003.8] Implement a `ScriptManager` to handle script loading, hot-reloading, and state isolation for pluggable components.
- [TSK-20260303-003.9] Provide a mechanism for Lua components to register and discover C++ services via a shared service registry.





## Implementation Plan

1. **Environment Setup & Infrastructure**:
    - Initialize `cmake-projects/scripting` with a `CMakeLists.txt` that pulls Lua 5.4 and `sol2` (via `FetchContent` or system packages).
    - Create a central `LuaEngine` class to encapsulate the `sol::state` and basic configuration.

2.  **Core Type Bindings**:
    - Implement `sol::usertype` mappings for `quasar::coretypes` (e.g., `Variant` conversion, `Timestamp` arithmetic, `Status` checks).
    - Map `quasar::named` registry to a Lua-accessible global or module to enable object lookup by string identifiers.

3.  **Modular Binding Registry**:
    - Define a `ILuaModule` interface or a registration callback mechanism.
    - Implement a `BindingManager` that allows external libraries to push their `sol::table` definitions into the `LuaEngine` during initialization.

4.  **Component System & Lifecycle**:
    - Define `ScriptComponent` with hooks for `on_init()`, `on_update(dt)`, and `on_shutdown()`.
    - Implement the `ScriptManager` to handle the mapping between `.lua` files and `ScriptComponent` instances.
    - Integrate a file-system watcher (e.g., `efsw` or similar) within `ScriptManager` to trigger hot-reloading of script states.

5.  **Service Discovery Bridge**:
    - Expose the C++ `ServiceRegistry` to Lua, allowing scripts to call `get_service("name")` and receive a bound proxy object.

6.  **Testing & Documentation**:
    - Create unit tests for `Variant` interoperability.
    - Provide a "Hello World" Lua component sample demonstrating lifecycle hooks and service access.

# Test and validation

- Verify `sol2` compatibility strictly on **Debian 12** and **Debian 13**.
- Validate hot-reloading stability under intensive data flow conditions.
- Perform automated memory leak checks (Valgrind/ASan) to prove deterministic resource cleanup.
- Create a comprehensive test suite for Lua component lifecycle hooks (`on_init`, `on_update`, `on_shutdown`), rigorously verifying proper unloading.

## Expected result

A fully functioning Lua 5.4 scripting bridge integrated seamlessly within the component framework, enabling memory-safe dynamic script execution.
